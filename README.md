# WatchGov — congressional data pipeline

An open pipeline that builds a structured, per-member dataset on the U.S. House of
Representatives across three dimensions:

- **Voting & policy alignment** — where each member stands on 5 policy topics, scored by
  LLM analysis of the bills they voted on, sponsored, and cosponsored.
- **Campaign finance** — who funds each member, broken down by small-dollar vs. large
  individual vs. PAC vs. party vs. self-funding, plus PAC profiles and outside spending.
- **Legislation** — bill details, votes, sponsorship, and committee activity.

The pipeline pulls from public government APIs (Congress.gov and OpenFEC) and an LLM, and
aggregates everything into one JSON file per member. **The generated dataset is committed to
this repo** ([`pipeline/output/`](pipeline/output/)), so you can use the data directly
without running anything or obtaining any API keys.

Source data is public-domain U.S. government work; the code in this repo is MIT-licensed
(see [LICENSE](LICENSE)).

> **Scope of the current dataset:** 431 House members · 119th Congress (2025–2026) · 2024 FEC
> cycle. It covers sitting House incumbents only — no Senate, and no non-incumbent challengers
> yet.

## Using the data (no setup required)

Every member file is plain JSON. For example, to read one member's top policy alignments:

```python
import json

member = json.load(open("pipeline/output/s5_alignment/NY_14.json"))
print(member["profile"]["name"])
for topic in member["alignment"]["topics"][:5]:
    print(f'  {topic["topic_name"]:<24} {topic["alignment"]:+.2f}  ({topic["confidence"]})')
```

## Running the pipeline yourself

You only need this if you want to refresh the dataset, extend it, or change the methodology.

### 1. Get API keys

- **api.data.gov key** — one key works for *both* Congress.gov and OpenFEC. Rate limits are
  per key, so you can add several and the pipeline will round-robin across them (one finance
  thread per key). Sign up at https://api.data.gov/signup/.
- **OpenRouter key** — only needed for the `analysis` stage (LLM topic scoring). Get one at
  https://openrouter.ai/. This stage costs money (see below); the other four stages are free.

Copy [`.env.example`](.env.example) to `.env` and fill in your keys:

```bash
cp .env.example .env
# then edit .env:
#   CONGRESS_API_KEY_1=...   (add _2, _3, ... for more throughput)
#   OPENROUTER_API_KEY=...
```

### 2. Install

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### 3. Run

```bash
python pipeline/run.py            # interactive menu: pick stages
python pipeline/run.py members    # run a single stage
python pipeline/run.py members finance bills analysis alignment   # all, in order
python pipeline/run.py --force alignment   # re-run even if output exists
```

Stages run in this order and build on each other:

| Stage | What it does | Needs |
|---|---|---|
| `members`   | Congressional profiles, voting history, sponsored/cosponsored bills | api.data.gov key |
| `finance`   | Campaign finance from OpenFEC (funding breakdown, PACs, outside spending) | api.data.gov key |
| `bills`     | Deep-dive detail for every referenced bill | api.data.gov key |
| `analysis`  | LLM topic scoring of bill text | OpenRouter key ($) |
| `alignment` | Aggregates votes + sponsorship + analysis into per-topic scores | — |

Raw API responses are cached under a gitignored `data/` directory (~2 GB when full) and
reused on re-runs, so re-running a stage is cheap and resumable.

## How the alignment score works

Full rationale — including the worked failure cases that shaped it — is in
[ALIGNMENT_QUALITY_PLAN.md](ALIGNMENT_QUALITY_PLAN.md). In brief:

A member's stance on a topic is **an evidence-weighted estimate with a confidence**, not a raw
average of recent votes. Each bill a member engaged contributes one signal, weighted by the
strongest role they took on it:

- **Vote** on final passage — directional (Yea `+`, Nay `−`), weight `1.0`. Procedural and
  amendment votes carry no weight and are excluded (they're party-discipline noise, not stance).
- **Sponsored** a bill — a strong endorsement of its direction, weight `0.8`, always `+`.
- **Cosponsored** — weaker support, weight `0.4`, always `+`.

For each topic, the LLM assigns every bill a score in `[-1, +1]`, and the per-topic alignment is:

```
alignment = Σ(weight · sign · score) / (Σ(weight · |score|) + K)
```

where `K = 1.0` is an **evidence-shrinkage** term that pulls thinly-evidenced topics toward
neutral, so a member who barely engages a topic can't show a full-strength bar. Every topic
also carries a `confidence` bucket (low / medium / high) from how many signals back it, and a
`salience` (that topic's share of the member's total legislative attention).

The LLM scoring itself uses a **"centrality is decisive"** rule (a buried clause can't dominate
a sprawling bill) and a **policy-area prefilter** (each bill is scored only on topics its
Congress.gov policy area is relevant to — so, e.g., a defense bill is never asked about LGBTQ
rights). See [services/congress/prompts.py](services/congress/prompts.py) and
[services/congress/topics.py](services/congress/topics.py).

### Which model scored this data

The committed analyses were produced with **`x-ai/grok-4.3`** at **temperature 0**, matching
[`config.json`](pipeline/config.json)'s `llm_model`. (The `gemini-2.5-flash` runs referenced in
`scripts/` and the test fixtures were A/B scoring experiments — their output lives in separate
experiment directories, not the live dataset.) Analysis files record their `llm_model` and
`temperature` inline, so every score is traceable to exactly what produced it.

### Known limitations

This is an inference over messy public data, and it has honest failure modes:

- **Protest votes read as opposition.** A `Nay` is scored as opposition even when it means "this
  bill didn't go *far enough*" (e.g. a hardliner voting against a border bill they find too soft).
  A maverick/dissent layer is planned but not built.
- **Thin-evidence topics.** Some topics are driven by very few bills; shrinkage and the
  `confidence` field mute these, but treat low-confidence scores with skepticism.
- **House-only, incumbents-only, 2024 finance cycle.** No Senate, no challengers, no
  multi-cycle finance trend yet.

## Tests

```bash
pytest tests/test_policy_areas.py    # pure logic — runs offline, no key needed
pytest                                # also runs the bill-scoring suite (see caveat)
```

`tests/test_bill_scoring.py` calls the **real** LLM against a handful of curated bills and
asserts each score lands in a sane band (the model is non-deterministic, so exact-equality
would be flaky). It **requires `OPENROUTER_API_KEY`, hits the network, and costs a few cents**
per run — without a key it skips cleanly, so a green run there may just mean "skipped." These
tests are not suitable for unattended CI as written.

- **Legislative data** — [Congress.gov API](https://api.congress.gov/), a public-domain work
  of the U.S. government.
- **Campaign finance data** — [OpenFEC](https://api.open.fec.gov/) (Federal Election
  Commission), public domain.

  [unitedstates/images](https://github.com/unitedstates/images) collection.
- **Topic scores** are LLM-generated inferences over the above, not official classifications.
